# 头歌妈妈 · touge.mom

头歌妈妈提供面向同学的课程执行服务。用户使用头歌账号登录，选择要处理的课堂，或一键处理全部活动课堂中的未完成作业，然后查看服务进度。用户端和管理端采用暖纸色、深棕顶栏、珊瑚强调色与用户提供的头歌妈妈图形 logo；费用、模型配置和内部故障由管理员处理。

头歌账号就是平台账号，无需另行注册、设置本站密码。登录页支持账号密码、头歌绑定手机号的短信验证码，以及已绑定头歌账号的微信扫码。服务端核验头歌返回的数字用户 ID，自动建立平台身份与个人数据分区；三种方式共用平台账号状态检查和站内 HttpOnly 会话。卡密功能已下架；定价、支付、套餐和周期额度尚未实现，不将模型成本展示成用户余额。

## 用户端与管理端

用户端主要动作是登录、选择课堂或一键处理全部未完成作业、查看完成状态。符合条件的失败、已停止或中断作业可点击“重新执行”，已满分内容自动跳过；仍在执行的作业可先请求停止，等待后台结束后再重新执行。重复点击复用同一个后续任务。需要核对上游结果的异常继续交给管理员，不要求用户理解模型、候选、自测和协议错误。另提供“问题反馈”工单，可提交问题、补充说明和查看管理员回复；用户只能访问本人的工单。

管理端供服务人员查看用户状态、任务详情、模型台账汇总、问题反馈和操作审计；可以回复工单、调整工单状态、管理账号状态（禁用时撤销会话并请求停止任务）、停止任务。管理员权限来自服务端配置与角色记录，不由头歌教师身份或前端页面切换授予。

课程状态与执行记录分别展示：最新成功同步且未过期的必做作业列表确认未完成数为零时，课程显示“已完成”；旧失败记录保留当次进度并显示“待跟进”。只有等待或运行中的安排计入“处理中”，暂停后的记录与未完成子项不再暗示后台仍在执行；是否能重新执行仍由服务端能力标记决定。

含未确认提交结果的整份作业、课程或全部课程安排，另提供“复核并继续”。后台先只读核对原课堂、作业和关卡的最新成绩，确认不确定内容已经满分或无需安排后，再继续剩余内容；核对仍未通过时保留进度和原因，可以再次复核，不直接重放未知提交。用户端会明确显示“复核排队中”“正在复核”“复核后继续”或“复核未通过”，并沿用原任务进度，不把复核子任务显示成普通待跟进。管理员也能发起复核，使用原用户当前有效的登录连接；连接已过期时会明确提示请该用户重新登录。

自测阶段的编辑器校验异常与正式提交结果未知分别处理：只有本地持久记录证明原单文件代码执行尚未进入正式评测，复核才会允许重新处理未满分的关卡。版本发布后，已加载的新页面会在常规请求中检测资源更新并提示手动刷新，避免长时间显示旧界面；不会自动刷新或丢弃输入草稿。

登录页提供《用户准则》弹窗，以普通说明介绍服务方式与使用提醒，突出授权做题数据收集和题目/答案复用用途；所有弹窗仅内容区滚动，右上角关闭按钮保持可见，并支持 Escape 关闭。说明不保证账号不受上游规则或风控限制，并区分不持久化的密码/Cookie 与必要保留的身份、任务、工单和审计记录。源码公开可审阅；站内不展示仓库地址，用户可通过工单申请核验实现和 Git 提交记录。

登录后的左下角展示统一的题库收录数量，包括客观题、编程题、绘图题和三类合计；本地题目及具备完整匹配契约的外部答案统一去重计数，界面不区分验证状态。卡片同时展示当前用户的贡献题数与致谢；移动端在主内容下方展示。个人贡献按题目去重，不代表全站首次新增题数，缺少归因的历史采集不猜测。登录页及题库卡片感谢 [ppxxforever/fuck-educoder](https://github.com/ppxxforever/fuck-educoder) 提供题库支持，并保留《用户准则》入口。

登录后的只读采集默认遍历完整的活动及已结束课堂，不设置整次任务时限或清单数量、累计请求和流量上限。独立采集通道繁忙时排队，不再直接跳过其他账号；同账号进行中的扫描去重。请求超时、响应大小、速率控制和答案证据核验仍保留，已验证结果持续入库；完成清单遍历与成功核验全部答案是不同统计，未确认内容保留明确原因。

重复登录采用持久化的增量采集：仍轻量读取完整目录与成绩，已成功采集的关卡按用户隔离保存进度指纹和题库证据引用，核验成功后才写检查点。新满分、评测次数、关卡名单或实训身份变化立即补采；已确认且未变化的内容免去重复定位、题目、答案与文件读取。检查点最多复用 24 小时，到期重新深度读取，即使成绩不变也能发现内容更新；复用不延长到期时间。失败、未确认及不支持项目不记作采集成功，取消或重启后保留成功部分，下次继续补漏。题库证据失效也会取消检查点复用。管理端采集详情显示免重复读取题数和检查点复用关卡数。

侧栏展示按可核验记录累计的服务学生数和完成题数，同时列出北京时间今日完成数。累计学生按平台身份去重，题数按学生与目标单题去重，不将每日学生数相加；排除题库采集、已通过跳过及不可靠完成证据。课程信息展示授课教师与真实学生人数。登录后会限并发预取作业与考试列表，详情优先读当前会话内缓存，右上角可手动刷新；退出后清空缓存。

实际 API、身份隔离、用户准则和当前限制见 [平台与运维说明](docs/PLATFORM.md)。

## 服务架构

```text
用户端 / 管理端（web/src，TypeScript）
  ↓ 同源应用 API、HttpOnly 站内会话
Go HTTP 服务（cmd/web + internal/web）
  ├─ internal/platform：数字身份、个人分区、角色、反馈工单、审计
  ├─ internal/jobs：持久任务记录、有界并发与重叠目标调度
  └─ internal/taskservice：课程 / 全部课堂 / 作业执行
      ├─ internal/solver、answer、questionbank：求解、模型与题库
      └─ internal/educoder：唯一 Go 协议客户端
          ↓ 动态签名、服务端内存 CookieJar
        Educoder API
```

网页请求返回任务 ID，任务由当前 Go 进程内的 worker 和 goroutine 异步执行，不会为每次请求启动 CLI 子进程。全站、单账号、模型请求分别设并发边界；同账号的课程、整份作业和单关目标存在包含关系时串行调度，避免重复写入。

课程任务首先确认课堂属于当前账号，按完整必做关卡分数跳过已经满分的作业，再执行其他作业。上游明确标记为“选做”的关卡不执行，不计入待完成数量或完成分母；整份作业只有选做关卡时，不列入本次待完成作业。不能单凭关卡分值为零推断选做。某份作业需要人工处理时，保留诊断并继续处理其他作业；单份作业内仍保持逐关身份校验、有限修复与最终满分复核。结果未知的写入不会自动重放。详细语义见 [异步执行](docs/async-jobs.md)。

原站编译 UI、资源复用服务和 Node/TypeScript 协议客户端已经移除。TypeScript 仅用于浏览器，Go 承担协议、AI、题库和应用 API；Node.js 仅用于构建和前端测试。

## 课程作业的处理与核验流程

头歌妈妈按下面的流程处理课程作业。各题型的文件读写、运行环境和正式评测协议不同，具体 I/O 见对应题型说明。**每一步都必须留下可验证的结果；不能因为接口返回了数据就直接宣布通过。**

```text
登录并建立内存会话
  → 只读读取课程/作业目录与必做关卡
  → 按题型校验课堂、作业、关卡，以及需要时的实训/运行实例身份
  → 生成题型专用题目快照与执行契约
  → 按题型指纹查询候选（编程题 revision_hash + contract_hash；选择题独立 scope hash）
  → 选择候选并绑定当前题目、账号与题型所需的运行身份
  → 执行题型专用自测、环境准备或选择提交
  → 按协议保存/提交并读取证据（代码源码回读、图形文件 CAS 等；选择题无代码保存）
  → 发起正式评测，有限轮询终态；写请求结果未知时不盲目重放
  → 按题型核验测试结果、关卡满分、课堂进度和内容哈希（适用时）
  → 成功/失败/未知观察都保留验证历史；只有完整通过证据才晋级题库可复用状态与作业进度
  → 继续下一关；整份作业结束后再核验课程未完成数
```

### 1. 目录与身份核验

执行入口先读取当前登录用户能看到的课堂目录。课程实验使用上游 `type=4`，图文作业使用 `type=1`；图文作业进入目录和详情，但不会误送进实训执行队列。按题型绑定所需身份：通常包括平台用户、课堂、作业、关卡；需要实训或执行环境的题型还绑定实训、运行实例和环境。缺少或矛盾的身份字段时停止，不用“同名课程”“同名账号”猜测归属。

作业只遍历必做关卡。已确认满分的关卡可以跳过，但“已跳过”必须来自当前上游成绩证据；不能把选做关卡、缺失成绩或旧缓存当成完成。

### 2. 题目快照与题库匹配

编程题使用 `problem.Snapshot`，包含题干、可编辑文件、只读上下文、公开测试和执行契约；`revision_hash + contract_hash` 是编程候选查找键。`revision_hash` 精确覆盖题型、标题、题干、公开样例与约束（CRLF 规范化），不含当前文件字节或只读上下文；候选文件另由精确 `files_hash` 绑定。选择题使用独立客观题快照、题目/选项身份和 scope hash，不复用编程源码候选键。绘图和终端题有各自执行模式及验证边界。

编程题库候选按以下字段绑定：

| 字段 | 作用 |
| --- | --- |
| `revision_hash` | 编程题型、标题、题干、公开样例与观察到的约束修订指纹；不含当前文件字节和只读上下文 |
| `contract_hash` | 可编辑路径、语言/扩展名、入口/固定区、模板、环境和编辑模式指纹 |
| `files_hash` | 候选实际文件内容的精确哈希 |
| `source/provider/model` | 候选来源和生成来源，不等同于通过证据 |
| `verifications` | 自测、正式评测或工作区验证记录 |

候选优先级通常是：当前编程题指纹下的 `upstream_verified` → 可验证的人工/外部候选 → 有明确历史证据的窄范围复核 → 模型生成。前两类仍须在当前目标下完成正式评测和满分复核；题库命中不等于自动通过。同一修订、同一契约下源码字节已有完整正式满分证据的候选不再重复公开自测，直接正式评测，正式失败照常回到修复流程；其余候选先完成公开自测。平台资源紧张时 `game_build` 可能返回 `-2`（评测未启动），按资源不可用延后重试，不记为结果未知。

普通单文件代码若从 Windows 题库读到 CRLF，执行前只把 `CRLF` 转成编辑器实际保存的 LF，并为不同字节创建或复用独立候选；原候选、原验证和原哈希不改写。真实源码差异、路径差异、题目契约差异仍然严格阻断。

### 3. 代码题（`single_file` / 普通编辑器）

代码题的实际顺序是：读取 task 与 `rep_content` → 读取题干和公开样例 → 读取可编辑文件及可选只读主程序/头文件 → 绑定编辑器基线 → `update_file(evaluate=0)` 保存 → `log_output` + `/log` WebSocket 自测 → 确认源码读回 → `update_file(evaluate=1)` 获取评测上下文 → `game_build` → `game_status` 有界轮询。

自测帧需要完整解码并看到 `ProcessFinished`；输出比较允许题目样例约定的换行差异。非空预期对应的空输出、截断、连接中断或缺少结束帧都不是自测通过证据。自测接口本身可能不提供编译状态字段，这不同于正式评测；正式通过要求测试集数量为正、每条结果明确通过且编译成功、保存/提交源码哈希与候选一致，并在课堂进度中再次看到当前关卡满分。

保存或提交之后结果未知时不重放写请求。只有持久证据能证明“尚未进入正式评测”且目标、候选哈希、题目契约和自测记录全部一致，复核入口才可以重新做只读核验或有限重试。

### 4. 选择题（`objective`）

选择题不读取代码文件，也不调用 `update_file`、代码 WebSocket 或 `game_build`。链路是读取题干/选项/题型/媒体 → 生成或查询 `answers[]` 候选 → `choose_build.json` 提交 → 读取上游返回 → 重新读取目标关卡分数和课堂进度。若提交后的关卡分数明确达到满分、返回题数与题目总数一致，且上游若公开逐题正确数也与题数一致，可在没有逐题 `test_sets` 时确认整关满分；逐题结果主要用于部分得分时定位题目和记录可复用的单题答案。题目数量、可核验的满分分值缺失或矛盾时保持 `unconfirmed`。平台分数是整关是否通过的裁判，但部分得分不够证明哪个单题选项正确；后续优化必须保存每次提交的候选、分数变化和失败原因，避免同一组合反复付费提交。

### 5. 绘图题（`graphic`，通常为 StarUML `.mdj`）

绘图题使用 `tab_type=3` 的运行环境，不走代码编辑器。链路是：`start.json` 获取临时 SSH/SFTP 连接 → 严格校验相对 `.mdj` 路径 → 在 `/data/workspace/myshixun` 下做 CAS 读回和原子写入 → 只提交目标文件 → `update_file(evaluate=1)` 获取 `sec_key/resubmit/content_modified` → `game_build` → `game_status` 轮询 → 任务详情和课堂满分复核。

路径必须拒绝绝对路径、`..`、`.git`、`secret`、符号链接和超大文件。临时 SSH 地址、密码、提交密钥不进入题目快照、模型输入、日志或任务记录。图形文件正式通过后仍要绑定当前账号、当前关卡、目标路径和完整满分证据；外部 `.mdj` 只能作为未验证候选。

### 6. Linux / Hadoop 独立终端题（`terminal`）

独立 Linux 终端题必须没有普通 `code_editor`，且唯一环境为 `tab_type=4`。它与“有代码编辑器并配有 `tab_type=4`”的 Hadoop 混合工作区是两种模式：混合题走专用路径，在同一运行实例准备 Hadoop 环境后通过终端执行候选脚本。独立终端 WebSocket 初始化后只发送一次脚本，脚本按字节哈希校验后执行；退出码、完整输出、边界帧和所需运行身份确认后，才进入正式评测。

Hadoop 混合题在同一运行实例中最多执行一次固定环境准备（例如 `start-dfs.sh`），只读确认 HDFS 根目录可用，再执行候选脚本。环境准备回执不是代码通过证据；准备失败、结果未知或再次要求启动时停止模型修复，保留候选和诊断。终端题的工作区通过证明只说明这次工作区通过，不自动晋升为可跨账号复用的全局源码答案。

### 7. 任务状态、复核与停止

任务由 Go 进程内 worker 异步执行，客户端只拿任务 ID 和脱敏进度。`queued/running` 表示仍在执行；`failed/canceled/interrupted` 只有服务端明确返回 `can_retry` 才允许普通重试；提交未知、身份未知或保存哈希不一致走独立“复核并继续”，不直接重放未知提交。

复核先读取当前上游成绩和关卡身份，确认原不确定内容已满分、选做或截止后，才继续剩余内容。失败或未知的自测/正式评测也保留为验证历史；只有完整且绑定到当前候选与目标的通过证据才会晋级为可复用状态和作业进度。复核失败保留原进度和原因，不把短暂的复核状态显示为零进度，也不把历史失败改写成成功。管理员使用原用户当前有效的头歌会话，不使用管理员自己的账号代做。

## 任务中断与结果核验

任务显示“待跟进”“卡住”或“进度不动”时，可按以下顺序核对：

1. 只读检查 `jobs.sqlite` 中当前 owner 的任务状态、phase、request、progress 和 result；先确认是否已有 `queued/running`，不要重复创建批次。
2. 确认当前任务的 `course/homework/game/challenge` 身份、当前关卡位置和失败/未知 reason code。
3. 检查题库是否命中同一 `revision_hash + contract_hash`，再看候选的 `files_hash`、自测/正式验证和保存/提交源码哈希。
4. 只读检查上游当前成绩和任务详情；区分题库失配、编辑器回读差异、环境未就绪、评测未知、模型错误和真实题目冲突。
5. 只有证据证明可重试时才创建同范围、同幂等键的 retry/recover 子任务；不清零计费、不修改 grader、不把截图或猜测当成通过。
6. 修复后跑针对性测试和完整 Go/前端检查，再做版本发布。线上部署前必须确认任务为空或有明确授权窗口，部署后核验 `/healthz` 的 `status/version/commit`，并让用户重新登录验证浏览器状态。

需要 Go 1.25+、Node.js 25+、npm：

## 数据与身份边界

`platform.sqlite` 保存已核验身份、角色、反馈工单及审计；`jobs.sqlite` 保存任务记录和幂等键；`questionbank.sqlite` 保存授权题库、验证证据与模型使用台账。三个数据库都位于应用数据目录，不能进入 Git、镜像或发布归档。工单标题与正文仅供本人及管理员处理问题，不进入题库，也不写入审计正文；请勿提交密码、Cookie、密钥或其他敏感凭据。关闭工单不会删除记录，当前没有自动到期删除功能。

上游密码不落库，上游 Cookie 和站内会话留在 Go 内存；浏览器只持有站内随机 HttpOnly Cookie。重启后需要重新登录，已持久化的个人身份与任务历史保留。未完成任务会被标记为中断或待核验，不会被自动重放。

旧调试版本按登录名 hash 保存的任务不会自动认领到新平台身份。同名登录名、教师标识或客户端传入的 owner 均不能作为迁移依据。当前为单实例 SQLite 服务，不宣称支持分布式 worker、跨节点会话或支付结算。

## 验证与发布

Go 检查建议从干净的 Git worktree 执行。开发机主目录可能保留被 `.gitignore` 忽略的旧恢复快照；Go 的递归包发现仍可能扫描这些目录，导致 `go test ./...` 编译到历史快照而非当前源码。发布前应在干净 worktree 中基于最新 `origin/main` 检查，并确认没有夹带其他会话的改动或恢复材料。

```powershell
go test ./...
go vet ./...
npm test
npm run typecheck
python scripts/check-private-data.py
.\scripts\release.ps1 -Message 'Describe the completed change'
```

每个完成的小改动增加 patch、更新 CHANGELOG、通过相关测试和隐私检查，再创建 commit、annotated tag，并通过 SSH 推送到 `git@github.com:RoseKhlifa/Educoder-tools.git`。不修改已发布标签，不 force-push。

服务监听 11454，部署主机通过本机 `ssh main` 连接；`touge.mom` 的 HTTPS 反代由用户在 1Panel 管理。本项目不创建 Nginx/OpenResty 配置。


截止状态：用户端作业列表只展示仍可安排的作业。服务端优先使用头歌返回的 `已截止 / 已结束 / closed / ended` 状态，并按 `end_time / deadline / end_date` 的上海时间兜底判断；缺少日期不当作截止。补交作业只有在上游明确给出有效延长截止时间时才保留。`course` / `all` 任务在规划和每份作业开始前都会复核截止状态，已截止作业不会进入运行实例、模型调用或提交；执行中跨过截止时间时停止后续关卡。历史题库采集仍读取原始列表，以保留已完成作业的核验记录。


管理端任务列表按用户、课程、作业与当前关卡、状态及带单位的进度、具体原因分别展示。姓名通过平台身份在服务端关联，不依赖前端最近100位用户列表；课程与作业名称来自已验证的上游列表及历史执行结果，并保存在仅用于显示的目录中。历史账号缺乏身份关联时明确标记“历史账号未关联”，不按登录名哈希认领。原始任务标识、原因码与诊断放在默认折叠的技术记录中；普通用户任务接口不增加这些管理信息。
